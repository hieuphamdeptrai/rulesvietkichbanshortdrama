# v4.3 — MASTER SELF-TEST, CERTIFICATION & RELEASE READINESS ENGINE

**Frozen design history.** Runtime consolidation does not delete these rules.

**Current operational owner:** `modules/15-onboarding-certification.md`

## Frozen rules
- **H-43-001** — Self-test and certification apply separately to the SDCS system/repository and to individual story projects.
- **H-43-002** — System Valid does not imply Project Valid, and Project Valid does not imply System Valid.
- **H-43-003** — Certification requires evidence that promised capabilities operate; it is not a feeling of completeness.
- **H-43-004** — Self-test pyramid: File Integrity→Schema Integrity→Module Integrity→Routing Integrity→Behavioral Tests→End-to-End Tests.
- **H-43-005** — Required system files include README/SYSTEM/CHANGELOG/sdcs manifest/modules/schemas/templates/tests/validation/presets/examples as applicable to release profile.
- **H-43-006** — Missing critical required files, unregistered modules, broken module references, or unresolved critical dependency cycles block release.
- **H-43-007** — Module registry records ID/version/file/purpose/activation/dependencies/status.
- **H-43-008** — Capability Registry maps each promised capability to an owner module and detects gaps or conflicting ownership.
- **H-43-009** — Major/testable rules need stable Rule IDs and a Rule Registry with source/severity/type/scope/validator/tests.
- **H-43-010** — Rule types: INVARIANT/HEURISTIC/GATE/PROJECT-CONFIGURABLE/PRODUCTION.
- **H-43-011** — Rule conflicts must be detected; precedence uses explicit invariant, state/genre-specific scope, documented refinement, then heuristic—not silent newest-wins deletion.
- **H-43-012** — No-Lost-Rule Test requires every meaningful rule from v1.0 onward to remain ACTIVE/REFINED/SCOPED/SUPERSEDED with lineage.
- **H-43-013** — SYSTEM.md need not contain every detail but must preserve core invariants/state/routing/authority/no-lost-rule/gates/memory/repair behavior and reliably route to full rules.
- **H-43-014** — Critical rules that exist only in history with no runtime retrieval path are compression failures.
- **H-43-015** — Routing tests must detect both UNDER-ROUTING and OVER-ROUTING.
- **H-43-016** — State routing must stop canonical screenplay generation when prerequisites are not satisfied unless explicit prototype mode is used.
- **H-43-017** — Fast/Prototype outputs must be labeled NON-CANON/PROTOTYPE.
- **H-43-018** — Canon safety test: alternative to locked truth creates a branch/unlock process rather than silently editing MAIN.
- **H-43-019** — Memory tests must prevent retired/stale branch facts from active authority.
- **H-43-020** — Audience simulation context must exclude unreleased Writer Truth.
- **H-43-021** — Continuity/payoff/scheduler/compiler/rescue/style/onboarding behaviors require dedicated behavioral tests.
- **H-43-022** — Behavior test case stores Input/Project State/Expected Routing/Expected Constraints/Forbidden Behavior/Pass Conditions.
- **H-43-023** — Maintain a small set of Golden Projects stressing basic mystery, romance relationship-mystery, production continuity, and broken-import rescue capabilities.
- **H-43-024** — Test fixtures include deliberately valid and invalid data with known expected validator outcomes.
- **H-43-025** — Every important real bug should become a regression test.
- **H-43-026** — Test categories: Static/Behavior/Narrative/Regression/Release; subjective narrative tests explicitly use AI/Human judgment rather than fake determinism.
- **H-43-027** — Test severity: BLOCKER/REQUIRED/RECOMMENDED/OPTIONAL.
- **H-43-028** — Stable release requires all Blocker tests passing, Required tests passing or documented exception, and zero unresolved Critical conflicts.
- **H-43-029** — System maturity may be ALPHA/BETA/RC/STABLE; design completion must be distinguished from repo implementation completion.
- **H-43-030** — Distinguish DESIGN CERTIFIED / REPO CERTIFIED / PROJECT CERTIFIED.
- **H-43-031** — Project certifications are scope-specific: CONCEPT READY / BLUEPRINT READY / WRITING READY / PRODUCTION READY / RELEASE READY.
- **H-43-032** — Concept Ready requires viable premise/genre-format/story lock/core truth direction and no critical contradiction.
- **H-43-033** — Blueprint Ready requires locked Final Truth/characters/arcs/mystery/clue-payoff/escalation/finale direction/lint pass.
- **H-43-034** — Writing Ready requires Episode Grid/current state/style baseline/knowledge/relevant clues/format.
- **H-43-035** — Production Ready requires approved screenplay/production profile/continuity/critical refs/no blocking lint/future setup check/style lock.
- **H-43-036** — Release Ready requires story QA/production QA/continuity/audio-text consistency/no unresolved critical issue.
- **H-43-037** — Certification artifact records target/result/passed gates/failed gates/exceptions/open risks/next actions.
- **H-43-038** — Certification statuses: PASS/PASS_WITH_RISK/CONDITIONAL/FAIL.
- **H-43-039** — Every PASS criterion links evidence; vague “quality insufficient” failures are invalid.
- **H-43-040** — Certification is version-bound and becomes stale when relevant upstream data changes.
- **H-43-041** — Freeze a release-candidate snapshot before major release; changes require new candidate/version.
- **H-43-042** — Design-history module versions v1.0→v4.4 are distinct from packaged semantic release versions such as SDCS 1.0.0.
- **H-43-043** — CHANGELOG preserves release change history while historical version files preserve design evolution.
- **H-43-044** — Release Manifest records release/modules/test status/schema version.
- **H-43-045** — Module completeness test requires Purpose/Rules/Integration/Failure-or-flags where relevant/Golden Rules and no truncation.
- **H-43-046** — Check numbering/path/template/schema/command/documentation consistency and coverage.
- **H-43-047** — Fresh AI reading SYSTEM.md + project Bootstrap must be able to resume project correctly.
- **H-43-048** — Cross-model handoff and chat-independence are critical portability tests; required state cannot live only in chat.
- **H-43-049** — Full E2E test must traverse Raw Idea→Seed→Premise→Truth→Characters→Blueprint→Grid→Card→Screenplay→Lint/Continuity→Production Pack at least once for relevant release profile.
- **H-43-050** — E2E failures must localize the failed layer rather than emit generic pipeline failure.
- **H-43-051** — Test profiles may include SYSTEM_CORE/SYSTEM_FULL/PROJECT_BLUEPRINT/PROJECT_WRITING/PROJECT_PRODUCTION.
- **H-43-052** — Smoke tests run after minor changes; full suite runs at release candidate.
- **H-43-053** — Use change-impact/dependency information to select targeted regression tests between full runs.
- **H-43-054** — System health dashboard may show tests passing/failing/coverage gaps/stale certification.
- **H-43-055** — Coverage means capability coverage, not only code line coverage.
- **H-43-056** — Critical capabilities such as canon protection, branch isolation, audience firewall, memory authority must have tests.
- **H-43-057** — Certification exceptions require reason/scope/risk/expiry and cannot silently waive critical invariants.
- **H-43-058** — Track system debt (documentation/test/schema/tooling) separately from story debt; stable release has zero critical system debt.
- **H-43-059** — Unknown status on a critical capability is not a pass.
- **H-43-060** — Negative/adversarial tests verify what the system must refuse/prevent, including premature screenplay, stale production, silent canon overwrite, spoiler leak.
- **H-43-061** — User override remains authoritative but must go through explicit unlock/ripple/update rather than silent corruption.
- **H-43-062** — Test that the system remains non-bureaucratic for simple tasks and scales complexity to project size.
- **H-43-063** — UX certification evaluates question burden/clarity/momentum/actionability/jargon exposure.
- **H-43-064** — Artifacts must be readable, nonredundant, purpose-specific, and actionable.
- **H-43-065** — Anti-bureaucracy test prevents small projects from generating excessive ledgers/files.
- **H-43-066** — Rescue robustness tests inject mid-project conflict and verify preservation/minimum intervention.
- **H-43-067** — Failure-recovery tests ensure regression detection and rollback are possible.
- **H-43-068** — Migration/backward-compatibility/deprecation/archive/source-authority tests protect older projects and retired data.
- **H-43-069** — Explicit current user/project decisions may override older locked decisions only through proper recorded change handling.
- **H-43-070** — System certification scoring cannot override hard fails.
- **H-43-071** — System release hard fails include lost prior core rules, broken registry, untested critical route, silent canon overwrite, stale memory authority, firewall failure, branch contamination, chat dependence, invalid critical schema, SYSTEM/module contradiction.
- **H-43-072** — Project Production Ready hard fails include unresolved core truth, Critical logic/continuity, broken major clue/payoff, script/card inconsistency, missing critical asset/ref, unchecked future setup.
- **H-43-073** — Certification is structural/process proof, not a guarantee of artistic masterpiece.
- **H-43-074** — Before release perform Master Audit across v1.0→current for Lost Rule/Duplicate Rule/Contradiction/Dead Module/Missing Integration/File/Test.
- **H-43-075** — Maintain Rule History/Lineage tracing foundational rules from origin through refinements to current enforcement.
- **H-43-076** — Historical versions must be preserved; recommended packaging uses HYBRID architecture: frozen historical files + consolidated operational modules + lineage proof.
- **H-43-077** — Consolidated modules may centralize duplicated rules only after every source rule is mapped.
- **H-43-078** — Rule mapping status may be PRESERVED/REFINED/SCOPED/SUPERSEDED; unmapped important rules block release.
- **H-43-079** — Self-test commands may expose /selftest /certify /regression but natural language remains valid.
- **H-43-080** — Self-test output defaults to result/blockers/risks/next action; full logs are optional.
- **H-43-081** — Fail fast on critical static failures before expensive subjective tests.
- **H-43-082** — Project certification order: source integrity→lint→continuity→story tests→simulation→red-team→scoring→production readiness→certificate.
- **H-43-083** — Do not run Full System Self-Test every message; use smoke tests during development and full tests at release milestones.
- **H-43-084** — Each test labels AUTOMATABLE/AI-JUDGMENT/HUMAN-REVIEW.
- **H-43-085** — Final artistic approval may remain human/user; certification supports authorship rather than replacing it.
- **H-43-086** — Core Release Boundary permits stable Story OS first and optional Production OS later.
- **H-43-087** — Self-certification bias is mitigated with deterministic checks, adversarial tests, fixed fixtures, evidence, and independent Certification Auditor role.
- **H-43-088** — Certifier assumes “not ready until evidence proves ready” and must explain PASS/FAIL/CONDITIONAL.
- **H-43-089** — Subjective tests use fixed rubrics/prompts/evidence to reduce variance.
- **H-43-090** — Golden projects can serve as benchmarks to detect quality/process/UX regressions from new modules.
- **H-43-091** — Each future proposed core module must pass a Module Value/Admission test: real failure, unique capability, reusability, integration value, complexity justification.
- **H-43-092** — Once all core capabilities have owners and tests, Core Freeze activates; new core modules require a genuine capability gap.
- **H-43-093** — Final Self-Test principle: SDCS must prove not only that it can generate/repair stories but that its operating process preserves integrity, portability, and accumulated rules.
