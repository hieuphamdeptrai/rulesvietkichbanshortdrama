# v4.1 — FAILURE RECOVERY & STORY RESCUE ENGINE

**Frozen design history.** Runtime consolidation does not delete these rules.

**Current operational owner:** `modules/14-branching-rescue.md`

## Frozen rules
- **H-41-001** — Rescue Mode exists for projects that are weakening, structurally broken, stalled, or production-locked; default response must not be “rewrite everything”.
- **H-41-002** — Distinguish low score/weakness from failure that blocks goals or downstream progression.
- **H-41-003** — Rescue philosophy: identify what is broken, what still works, root cause, and minimum intervention.
- **H-41-004** — Before repair, create Preserve Locks: MUST PRESERVE / PREFER PRESERVE / FREE TO CHANGE.
- **H-41-005** — Rescue targets root cause rather than surface symptom.
- **H-41-006** — Classify failure level: F1 Local / F2 Sequence / F3 Arc / F4 Character-Relationship / F5 Core Structure / F6 Production-Locked.
- **H-41-007** — F1 should usually use local mutation rather than blueprint rewrite.
- **H-41-008** — F2 should repair sequence objective/reward/escalation/function variation before changing core truth.
- **H-41-009** — F3 may redesign an arc while preserving entry/exit state where possible.
- **H-41-010** — F4 repairs want/dependency/loyalty/secret/choice rather than adding irrelevant backstory.
- **H-41-011** — F5 may require Truth or Concept unlock only after evidence shows lower-level repair is insufficient.
- **H-41-012** — F6 prioritizes preservation of produced material via recontextualization/inserts/dialogue/edit/object meaning before large reshoots.
- **H-41-013** — Rescue triage considers severity, scope, production status, downstream reach, viewer impact, and repair cost.
- **H-41-014** — Rescue order: Canon/Logic→Character Motivation→Core Curiosity→Causality→Payoff→Escalation→Pacing→Style.
- **H-41-015** — Use recognizable failure signatures to diagnose premise/core truth/character/mystery/escalation/payoff/pacing problems.
- **H-41-016** — Rescue Diagnostic Card must record symptom/evidence/root cause/failure level/preserve/mutate/ripple.
- **H-41-017** — Consume v3.9 health data when available; do not diagnose solely from vague feeling.
- **H-41-018** — Run mechanical lint/continuity checks before creative redesign when the symptom may be structural data error.
- **H-41-019** — Rescue paths ordered by escalation: PATCH→REFRAME→RESTRUCTURE→REPLACE→ROLLBACK→UNLOCK.
- **H-41-020** — Patch is smallest intervention; Reframe preserves event but changes meaning; Restructure changes sequence/architecture; Replace swaps failed component; Rollback restores stable version; Unlock breaks a locked layer.
- **H-41-021** — Do not unlock Core Truth for a local episode weakness.
- **H-41-022** — Use the minimum effective intervention that restores failed function.
- **H-41-023** — When mechanism changes, preserve required Narrative/Character/Curiosity/Payoff/Production functions.
- **H-41-024** — A repair that fixes one subsystem but breaks multiple healthy systems is a failed repair.
- **H-41-025** — Rescue regression loop: Repair→Lint→Continuity→Simulation→Health comparison→Accept/Rollback.
- **H-41-026** — Rescue succeeds only if root issue improves, no Critical regression appears, important strengths remain, and rebuild cost is acceptable.
- **H-41-027** — Compare health before/after; net-negative repairs must be rolled back or replaced.
- **H-41-028** — High-impact rescue should be tested in isolated rescue branches, not directly applied to MAIN.
- **H-41-029** — Use Conservative/Balanced/Aggressive rescue options when meaningful.
- **H-41-030** — Rescue experiment question must state the failing goal plus what must be preserved.
- **H-41-031** — Produced material may be marked EDITABLE / ASSET_CREATED / GENERATED / FINALIZED to shape rescue strategy.
- **H-41-032** — Post-production rescue toolbox may include re-edit, insert, reaction insert, audio cue, VO, text, later scene, recontextualization, trim, reorder.
- **H-41-033** — Prefer soft retcon/recontextualization over hard retcon whenever prior observed facts can remain true.
- **H-41-034** — Before hard retcon, test wrong interpretation, incomplete information, hidden motive, hidden consequence, and missing relationship context.
- **H-41-035** — Same event with new meaning is a preferred late-stage rescue technique when fair.
- **H-41-036** — Weak event may be rescued by stronger consequence rather than replacement.
- **H-41-037** — Stale mystery may be rescued by answering earlier and shifting WHAT→WHY/CONSEQUENCE.
- **H-41-038** — Overcomplexity may be rescued through compression, deletion, or merging characters/suspects/props/mysteries/locations.
- **H-41-039** — Deletion is a valid repair; do not assume every rescue requires adding material.
- **H-41-040** — Character merge must preserve compatible functions and re-audit secret/knowledge/motive.
- **H-41-041** — Character split is rare and justified only when clarity gain exceeds cast/complexity cost.
- **H-41-042** — A story-critical object may consolidate clue/memory/relationship/payoff efficiently.
- **H-41-043** — Boring middle often requires objective change rather than more events.
- **H-41-044** — Role reversal, power shift, information asymmetry, rooted deadline, personal cost, and choice can repair static engines.
- **H-41-045** — Premise rescue checks Curiosity Gap/Story Lock/Personal Stake/Series Engine/Final Truth Potential.
- **H-41-046** — One-twist premise should deepen motive/relationship/system/self-implication rather than add random twists.
- **H-41-047** — Core Truth rescue should strengthen protagonist relevance, emotional meaning, motive, and reframe before changing WHO.
- **H-41-048** — Final Truth should be explainable simply; complexity requiring long exposition is a rescue signal.
- **H-41-049** — Finale rescue priority: Hero agency→existing clue convergence→truth→choice→aftermath; do not introduce an unseeded solution.
- **H-41-050** — Midpoint rescue asks what actually changes afterward in objective/relationship/identity/stakes/role/moral position.
- **H-41-051** — Arc rescue preserves valid beats and required endpoints while rebuilding the failed turning point/objective/escalation.
- **H-41-052** — Weak episode rescue checks primary question/objective/state change/reward/consequence/cliff before adding a twist.
- **H-41-053** — Confusing episode rescue should reduce/reorder/visualize information before adding exposition dumps.
- **H-41-054** — Predictable twist may be rescued by earlier reveal, changed motive/meaning/consequence, or aftermath focus before changing culprit.
- **H-41-055** — Random twist must gain footprints, causality, and character relevance or be removed.
- **H-41-056** — Weak villain is repaired through rational goal/adaptation/relationship/leverage/cost of victory, not simply “more evil”.
- **H-41-057** — Passive protagonist rescue converts external plot turns into choices/actions caused by protagonist agency.
- **H-41-058** — Flat relationship is repaired through dependency/asymmetry/choice/shared secret/leverage rather than repetitive misunderstanding.
- **H-41-059** — Weak romance requires something the characters uniquely need from each other; intimacy should be plot-driven.
- **H-41-060** — Mystery rescue adapts differently for confusion, obviousness, and staleness.
- **H-41-061** — Unfair twist should preferably reframe existing innocuous material before inserting loud last-minute clues.
- **H-41-062** — Weak payoff should improve meaning/consequence/choice before increasing answer complexity.
- **H-41-063** — Weak cliff should create a specific new question rather than generic interruption.
- **H-41-064** — Style drift can receive a style pass without rebuilding story.
- **H-41-065** — Production-impossible scene should preserve story function and mutate execution.
- **H-41-066** — Continuity rescue is severity-based; regenerate critical story-significant mismatches while tolerating harmless drift.
- **H-41-067** — If multiple patches accumulate around the same subsystem, stop patching and move one layer upstream.
- **H-41-068** — Temporary patches must be labeled and cannot silently become permanent.
- **H-41-069** — Activate only the minimum relevant modules for a rescue case.
- **H-41-070** — Enter Rescue Mode on Critical health issues, repeated regression, stall, patchwork, or major production blocker.
- **H-41-071** — While project health is RED, pause new downstream generation until stabilized.
- **H-41-072** — Stabilization: freeze branch→save checkpoint→map damage→preserve strengths→build rescue options.
- **H-41-073** — Rescue checkpoint records project version/health/canon/current state/produced assets.
- **H-41-074** — Damage Map and Blast Radius identify affected canon/arcs/episodes/clues/characters/artifacts/production.
- **H-41-075** — Blast radius and failure severity are distinct dimensions.
- **H-41-076** — Rescue cost matrix compares quality gain, story ripple, rewrite cost, production cost, risk, and effort class.
- **H-41-077** — Avoid sunk-cost bias: preserve actual value, not merely expensive material, while recognizing production cost as real dependency.
- **H-41-078** — Story Integrity > Character Logic > Audience Trust > Payoff > Production Cost > Novelty during rescue.
- **H-41-079** — Rescue Plan tells user failure/root cause/preserve/recommendation/changes/ripple/validation without panic language.
- **H-41-080** — Low rescue confidence should trigger branching/experiment rather than confident direct rewrite.
- **H-41-081** — Exit Rescue Mode only when Critical=0, root issue resolved, regression pass complete, health stable/improving, scheduler recalculated, and sources current.
- **H-41-082** — If rescue fails, rollback checkpoint before trying next branch; never stack fixes on failed unrolled-back repairs.
- **H-41-083** — Maintain Rescue History/Case files with rejected attempts to avoid repeating mistakes.
- **H-41-084** — Published story turns past observed facts into strong locks; future episodes may reinterpret but should not deny what viewers clearly saw without justified retcon.
- **H-41-085** — Production accidents can be ignored, patched, or intentionally adopted into canon only after audit; do not turn every generation error into lore.
- **H-41-086** — Before story rewrite, classify failure layer: Story/Screenplay/Performance/Visual/Edit/Audio and repair at the lowest correct layer.
- **H-41-087** — Do not escalate to story-level changes for an execution problem until lower-layer causes are ruled out.
- **H-41-088** — Maintain a rescue pattern knowledge base as guidance, never one-size-fits-all recipes.
- **H-41-089** — Rescue candidates can be scored on Root Cause Fit/Strength Preservation/Curiosity/Logic/Character/Payoff/Ripple/Production/Simplicity/Regression Risk.
- **H-41-090** — Stop repair once root problem is gone, gates pass, health is stable, and remaining changes are polish/preference.
- **H-41-091** — Every major rescue performs a postmortem: what failed, why not detected earlier, what guardrail should improve, what new test/rule is needed.
- **H-41-092** — Failure→Root Cause→Repair→Postmortem→Guardrail→Story Test/Lint Rule/Dependency is the learning loop.
- **H-41-093** — System learning here means repo/project rules and tests improve; it is not hidden model training.
- **H-41-094** — Rescue UX should surface the few decisive facts and recommend a path rather than dump all errors.
- **H-41-095** — Minor/mechanical rescue may be autonomous; major canon changes require explicit decision/authorized autonomy.
- **H-41-096** — If constraints are mutually impossible, state the conflict and least-cost compromise rather than promise a magic rescue.
- **H-41-097** — Final Rescue principle: a mature Story OS need not never fail; it must detect, stop, localize, preserve, repair, validate, rollback, and learn from failure.
