# v4.4 — REPOSITORY PACKAGING, RELEASE & DISTRIBUTION ARCHITECTURE

**Frozen design history.** Runtime consolidation does not delete these rules.

**Current operational owner:** `modules/15-onboarding-certification.md`

## Frozen rules
- **H-44-001** — Package all design history through v4.4 as SDCS Story OS Release 1.0.0 while preserving every historical contribution.
- **H-44-002** — Final repository must be COMPLETE, NAVIGABLE, EXECUTABLE, TESTABLE, and EVOLVABLE.
- **H-44-003** — Repo is not a Markdown dump; separate entrypoint/runtime/knowledge/data/templates/QA/project workspace/history layers.
- **H-44-004** — Root should expose README.md for humans and SYSTEM.md/SKILL.md for AI runtime entry.
- **H-44-005** — Runtime layer contains orchestration/routing/state/authority/gates/context/commands and remains much smaller than the full knowledge base.
- **H-44-006** — Full detailed rules live in operational modules plus frozen history; SYSTEM.md is compressed runtime and must route to detail on demand.
- **H-44-007** — Use a HYBRID packaging strategy: preserve historical version files and create consolidated functional runtime modules.
- **H-44-008** — Historical v1.0→v4.4 files remain in repo and are never deleted during consolidation.
- **H-44-009** — Maintain Rule Lineage/Inventory mapping every meaningful historical rule to current operational owner/status.
- **H-44-010** — Rule status must be explicit: ACTIVE/REFINED/SCOPED/SUPERSEDED/HISTORICAL_ONLY; no silent removal.
- **H-44-011** — Consolidation removes repeated explanation, not operational conditions/exceptions/thresholds/scores/bans/failure modes/integration.
- **H-44-012** — Runtime registry (`sdcs.yaml`) maps functional modules to files, origins, activation, dependencies, and status.
- **H-44-013** — Distinguish semantic SDCS Release version (e.g. 1.0.0) from design genealogy versions v1.0→v4.4.
- **H-44-014** — CHANGELOG records packaged release changes; VERSION_HISTORY preserves design evolution; RELEASE_NOTES gives human summary.
- **H-44-015** — Do not choose a public license silently; license is a user/repository policy decision.
- **H-44-016** — Quick Start should allow a user/model to read SKILL/SYSTEM then initialize from a natural-language idea.
- **H-44-017** — Project workspaces use lean starter files and create additional data/scripts/production/audit files lazily.
- **H-44-018** — Each active project has a machine `project.yaml` and a compact derived `BOOTSTRAP.md` for portable restart.
- **H-44-019** — Bootstrap summarizes identity/state/locked canon/main characters/current arc/open loops/constraints/style/blockers/next action.
- **H-44-020** — Chat history is optional; repo/project sources must be sufficient for continuation.
- **H-44-021** — Distribution profiles may include Core/Lite/Full/Production, but the full GitHub repo is canonical distribution.
- **H-44-022** — Story Core should be independently complete; future Production OS should extend rather than bloat core.
- **H-44-023** — Extensions declare required core version/modules/schemas/tests/routes and do not mutate core silently.
- **H-44-024** — Presets are starting profiles, not plot templates, and remain overrideable by project config.
- **H-44-025** — Templates are grouped by Development/Writing/QA/Production/Handoff and document purpose/inputs/authority/minimum state.
- **H-44-026** — Schemas are versioned with registry/migration policy and backward compatibility.
- **H-44-027** — PATCH/MINOR/MAJOR semantic version policy distinguishes bugfix/compatible capability/breaking contract changes.
- **H-44-028** — Behavioral/default rule changes must be documented; no silent rule changes.
- **H-44-029** — Experimental capabilities live outside stable runtime until certified and pass module admission tests.
- **H-44-030** — Deprecated modules/fields map replacements and remain archived through a compatibility period.
- **H-44-031** — Documentation has distinct audiences: beginner README, AI runtime SYSTEM/SKILL, advanced docs, maintainer architecture/testing/versioning.
- **H-44-032** — CONTRIBUTING requires no-lost-rule, tests, lineage, registry, changelog, and overlap checks for additions.
- **H-44-033** — Future module standard should include Purpose/Activation/Inputs/Rules/Failure Modes/Integration/Validation/Artifacts/Golden Rules and optional machine metadata.
- **H-44-034** — Global Rule Registry contains important/testable rules with one primary owner to avoid conflicting definitions.
- **H-44-035** — Short runtime INVARIANTS should include curiosity progression, motivated action, silent-canon-change ban, twist footprints, earned payoff, persistent state, audience firewall.
- **H-44-036** — Commands are optional shortcuts; natural language remains primary UX.
- **H-44-037** — Tests package includes smoke/behavior/regression/e2e/fixtures/golden projects.
- **H-44-038** — Examples demonstrate system behavior but are never story-content defaults and must not contaminate user projects.
- **H-44-039** — Initial optional tooling should focus on project validation, reference checking, lint, bootstrap/context building, artifact compilation; core must work without Python.
- **H-44-040** — Core is AI-first and file-based; tooling enhances but does not define the system.
- **H-44-041** — Avoid vendor lock-in: model-agnostic rules/state/schema/artifacts; provider adapters are optional extensions.
- **H-44-042** — Primary distribution is Git repository; ZIP/single-context/skill package are derived transport formats.
- **H-44-043** — Single-file compact export is non-authoritative and points back to full repo for detailed rules.
- **H-44-044** — Story creative branches and Git repository branches are separate concepts and must not be conflated.
- **H-44-045** — Git history may support rollback/change history, but Story OS state cannot depend solely on Git semantics.
- **H-44-046** — Recommended repository development strategy may use main/develop/experimental while remaining simple.
- **H-44-047** — Static CI should validate paths/YAML/schema/rule registry/duplicate IDs/test fixtures before more subjective checks.
- **H-44-048** — Indexes such as Module Index/Version History/Capability Matrix/Rule Index should be generated where practical to reduce doc drift.
- **H-44-049** — Project starter remains lean and uses shared global templates rather than copying every unused template into each project.
- **H-44-050** — Explicit Source-of-Truth Policy defines authority: current explicit decision→Locked Canon→current authoritative state→approved blueprint/data→derived artifacts→drafts→ideas→historical/retired.
- **H-44-051** — Derived artifact never outranks source; summaries are caches and never outrank canon.
- **H-44-052** — Project archive stores superseded scripts/rejected branches/stale artifacts/snapshots and is excluded from normal retrieval.
- **H-44-053** — Project exports may be Writer/Production/Full Archive/Handoff; Handoff is critical to long-term reuse.
- **H-44-054** — Fresh AI should be able to read repo entrypoints + project bootstrap, identify state, retrieve correct module, preserve canon, and continue.
- **H-44-055** — Documentation drift must be tested; generated indexes/registries should minimize duplicated manual facts.
- **H-44-056** — Release artifacts/manifests record release/schema/modules/capabilities/tests/known limitations.
- **H-44-057** — Document known limitations honestly; Story OS 1.0 may leave image/video prompt engineering, voice orchestration, and edit automation to Production OS.
- **H-44-058** — Stable Story Core is complete when it can onboard/design/write/remember/validate/simulate/branch/repair/handoff reliably.
- **H-44-059** — After v4.4 enter Feature Freeze/Consolidation Mode; no automatic v4.5.
- **H-44-060** — Implementation order: Rule Inventory→Taxonomy→Lineage→Runtime→Data/Schemas/Templates→QA→Examples→Release.
- **H-44-061** — Rule Inventory is exhaustive for meaningful rules; duplicate historical rules may map to one operational rule only when meaning is preserved.
- **H-44-062** — Do not retain development numbering as runtime organization; runtime modules load by function while history preserves genealogy.
- **H-44-063** — State + task routing controls whether a requested action is allowed/provisional/blocked.
- **H-44-064** — Context budget follows progressive disclosure: minimum sufficient modules, never load entire system blindly.
- **H-44-065** — Initial core should require no heavy infrastructure/database/vector DB; file-based Markdown/YAML/JSON remains canonical and Git-friendly.
- **H-44-066** — Optional indexing/vector search may be added later without changing canonical sources.
- **H-44-067** — Operational modes (Lite/Standard/Full) alter overhead, not core story integrity rules.
- **H-44-068** — Project manifests record release/schema compatibility; future lock/version files may support reproducibility.
- **H-44-069** — Deterministic system behavior should include authority/routing/validation/state even though creative output can vary.
- **H-44-070** — Folder separation and generated/source/archive/visibility headers should reduce accidental authority inversion and spoiler leakage.
- **H-44-071** — File naming and registry conventions must be stable; registry outranks filename ordering.
- **H-44-072** — Release checklist requires all history versions, Rule Inventory/Lineage, mapped runtime modules, validated SYSTEM/README/schema/templates/tests/E2E/fresh-session recovery/changelog/limitations.
- **H-44-073** — Before Production or Release certification, critical issues must be zero and artifacts/current references validated for that scope.
- **H-44-074** — Final package must pass v4.3 certification before claiming Stable.
- **H-44-075** — Release freeze means meaningful changes invalidate certification and require appropriate re-tests/version bump.
- **H-44-076** — Hotfix/minor/major releases follow semantic scope; released history is not retroactively rewritten.
- **H-44-077** — Future Production OS may version independently while declaring compatible SDCS Core requirement.
- **H-44-078** — Final UX: clone/download repo→AI reads SKILL/SYSTEM→user gives idea→auto-onboarding; months later repo+bootstrap resumes without recap.
- **H-44-079** — Human collaborators should understand canon/intent/issues from project files without reading old chats.
- **H-44-080** — Machine tooling should parse the same project source used by humans and AI.
- **H-44-081** — Prompt is not the product; SDCS is a versioned, tested, stateful, portable Story Operating System repository.
- **H-44-082** — Core stack: User Intent→Onboarding→Story OS→State/Canon→Memory/Retrieval→Story Engines→Compiler→Validation/Simulation/Red-Team→Health/Scheduler→Lock/Commit/Rescue→Repository.
- **H-44-083** — v1.x–v2.x primarily accumulated narrative intelligence; v3.x system intelligence; v4.x identity/robustness/productization.
- **H-44-084** — After v4.4 architecture is closed enough to implement; next work is repository build/certification, not more abstract versions.
- **H-44-085** — Implementation checkpoints may use build 0.1 root/history/registry→0.2 runtime/SYSTEM→0.3 modules→0.4 schemas/templates→0.5 tests→RC1→1.0.0.
- **H-44-086** — No-Lost-Rule Build Gate requires every historical rule mapped before consolidated runtime is certified.
- **H-44-087** — Repo build should be iterative and tested by layer rather than one unvalidated giant generation.
- **H-44-088** — Do not package as one giant prompt; do not consolidate without lineage; do not omit history; do not depend on chat; do not require heavy infra; do not advertise uncertified features; do not add core modules without a proven gap.
- **H-44-089** — Packaging means making accumulated knowledge/state/rules/history/workflow operable by someone who did not build it.
- **H-44-090** — Runtime must be much smaller than the knowledge base yet smart enough to retrieve the right detail.
- **H-44-091** — Full canonical distribution must survive new chat/new model/new machine/new time without losing canon, decisions, context, style, or operating structure.
- **H-44-092** — Core Freeze is a maturity behavior: quality is demonstrated by implementation, tests, real project performance, and reduced failure—not by endless module count.
- **H-44-093** — Final Packaging principle: Repository is the durable Story OS; chat is transient.
