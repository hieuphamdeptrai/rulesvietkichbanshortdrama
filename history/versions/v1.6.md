# v1.6 — MYSTERY & CLUE ENGINE

**Frozen design history.** Runtime consolidation does not delete these rules.

**Current operational owner:** `modules/05-mystery-clue.md`

## Frozen rules
- **H-16-001** — Give enough evidence to theorize, not enough for premature certainty.
- **H-16-002** — Every clue must move truth, theory, or twist preparation.
- **H-16-003** — Clue types: Direct / Behavior / Dialogue / Visual / Absence / Contradiction.
- **H-16-004** — Ideal clue has two lives: initial interpretation and true meaning.
- **H-16-005** — Maintain Micro / Arc / Core mystery hierarchy.
- **H-16-006** — Core clue often appears before audience knows its importance.
- **H-16-007** — Clue escalation can move oddity→character relevance→mystery relevance→theory→payoff.
- **H-16-008** — For 60–90s episodes, roughly one main clue plus optional secondary clue is a useful density baseline.
- **H-16-009** — Clue density is guideline, not rigid quota.
- **H-16-010** — Visibility: Obvious / Noticeable / Hidden-in-plain-sight.
- **H-16-011** — Invisible evidence does not count as fair setup.
- **H-16-012** — Fair play: rewatch should show solution was supported.
- **H-16-013** — Use echo repetition to reactivate clue with new meaning.
- **H-16-014** — Use pair/triangle/collision clue structures when useful.
- **H-16-015** — Red herring should be true enough to support inference.
- **H-16-016** — Red herring ideally has secondary payoff.
- **H-16-017** — Clue carriers can be object state / sound / costume / location / habit / memory.
- **H-16-018** — False memory should usually be true memory with wrong context/identity/time/meaning.
- **H-16-019** — Clue Ledger statuses: Open / Partial / Paid.
- **H-16-020** — Same data should support different interpretations until reveal.
